Multica는 기본적으로 이메일 인증 코드로 로그인하며 Google OAuth를 추가할 수도 있습니다. 기존 사용자는 언제든 다시 로그인할 수 있습니다. 가입 제한은 새 계정을 만들 수 있는지만 결정합니다.

## 이메일 인증 코드

사용자가 이메일을 입력하면 Multica가 6자리 인증 코드를 보냅니다. 코드는 10분 동안 유효하며 인증에 성공하면 브라우저에 로그인 cookie가 발급됩니다.

이메일은 Resend 또는 SMTP로 보낼 수 있습니다. 둘 다 설정하면 `SMTP_HOST`가 우선합니다.

### Resend 사용

1. [Resend](https://resend.com/)에서 발신 도메인을 인증하고 API key를 만듭니다.
2. 다음을 설정합니다.

   ```dotenv
   RESEND_API_KEY=re_xxxxxxxxxxxxxxxx
   RESEND_FROM_EMAIL=noreply@example.com
   ```

3. API 서비스를 다시 시작합니다.

`RESEND_FROM_EMAIL`은 Resend에서 인증한 도메인에 속해야 합니다.

### SMTP 사용

최소한 host와 발신 주소를 설정해야 합니다.

```dotenv
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USERNAME=multica
SMTP_PASSWORD=<password>
SMTP_FROM_EMAIL=noreply@example.com
```

일반적인 연결 방식은 다음과 같습니다.

| 환경 | 설정 |
|---|---|
| 내부 네트워크 익명 relay | `SMTP_PORT=25`, 사용자 이름과 비밀번호는 비워 둠 |
| STARTTLS | `SMTP_PORT=587`, 서버가 지원하면 기본적으로 TLS로 업그레이드 |
| 암시적 TLS | `SMTP_PORT=465` 또는 `SMTP_TLS=implicit` 명시 |

`SMTP_FROM_EMAIL`을 설정하지 않으면 `RESEND_FROM_EMAIL`을 사용합니다. 사설 CA 또는 자체 서명 인증서를 사용하려면 컨테이너 신뢰 저장소에 CA를 추가해야 합니다. `SMTP_TLS_INSECURE=true`는 인증서 검증을 건너뛰므로 신뢰할 수 있는 내부 네트워크에서만 임시로 사용하세요.

일부 엄격한 relay에는 유효한 EHLO 이름도 필요합니다.

```dotenv
SMTP_EHLO_NAME=mail.example.com
```

### 이메일 서비스가 없을 때의 동작

서버는 계속 시작되지만 인증 코드와 초대 링크가 이메일로 전송되지 않고 로그에만 기록됩니다. 로컬 개발에는 적합하지만 프로덕션 환경에는 적합하지 않습니다.

시작 로그에는 현재 `Resend API`, `SMTP relay`, `DEV mode` 중 무엇을 사용하는지 표시됩니다.

## 로컬 고정 인증 코드

로컬 자동화 테스트에서는 고정 인증 코드를 설정할 수 있습니다.

```dotenv
APP_ENV=development
MULTICA_DEV_VERIFICATION_CODE=888888
```

인증 코드는 6자리 숫자여야 합니다. `APP_ENV=production`에서는 고정 코드가 무시됩니다.

<Callout type="warning">
공개 인터넷에 노출된 인스턴스에서 고정 인증 코드를 사용하지 마세요. 프로덕션 환경에서는 `APP_ENV=production`을 사용하고 `MULTICA_DEV_VERIFICATION_CODE`를 비워 둡니다.
</Callout>

## Google 로그인

1. [Google Cloud Console](https://console.cloud.google.com/)에서 OAuth 2.0 client를 만듭니다.
2. Multica 프런트엔드의 callback 주소를 **Authorized redirect URIs**에 추가합니다.

   ```text
   https://multica.example.com/auth/callback
   ```

3. 다음을 설정합니다.

   ```dotenv
   GOOGLE_CLIENT_ID=xxxxx.apps.googleusercontent.com
   GOOGLE_CLIENT_SECRET=GOCSPX-xxxxxxxxxxxxxxx
   GOOGLE_REDIRECT_URI=https://multica.example.com/auth/callback
   ```

4. API 서비스를 다시 시작합니다.

Google Console과 `GOOGLE_REDIRECT_URI`의 주소는 프로토콜, 포트, 마지막 슬래시까지 완전히 같아야 합니다. 설정이 적용되면 로그인 페이지에 Google 로그인 버튼이 표시됩니다. 프런트엔드 이미지를 다시 빌드할 필요는 없습니다.

## 싱글 사인온(OIDC)

Multica는 표준 OpenID Connect를 사용하므로 discovery 문서를 공개하는 ID 공급자라면 모두 연결할 수 있습니다(Keycloak, Authentik, Okta, Auth0, Entra ID). 아래는 Keycloak 예시이며, 변수는 어느 공급자에서나 동일합니다.

### 1. ID 공급자에 클라이언트 등록

Keycloak에서 realm을 열고 클라이언트를 만듭니다.

- **Client type**: `OpenID Connect`
- **Client authentication**: `On` — Multica는 confidential client이며 항상 client secret을 보냅니다
- **Valid redirect URIs**: 아래 주소를 정확히 그대로 등록합니다

```text
https://multica.example.com/auth/oidc/callback
```

<Callout type="warning">
공급자는 바이트 단위로 대조하므로 프로토콜, 포트, 마지막 슬래시까지 같아야 합니다. 평소 로그인하는 Multica origin을 쓰세요. API를 별도 호스트에서 운영한다면 `/auth/oidc/callback`을 제공하는 **API** origin을 사용합니다.
</Callout>

클라이언트의 **Credentials** 탭에서 생성된 client secret을 복사합니다.

### 2. Multica 설정

```dotenv
OIDC_ISSUER=https://sso.example.com/realms/multica
OIDC_CLIENT_ID=multica
OIDC_CLIENT_SECRET=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
OIDC_PROVIDER_NAME=Keycloak
```

`OIDC_ISSUER`는 `/.well-known/openid-configuration`을 제공하는 기본 URL입니다. Keycloak에서는 `<base>/realms/<realm>`입니다. 재시작 전에 확인하세요.

```bash
curl -s https://sso.example.com/realms/multica/.well-known/openid-configuration | head
```

callback URL은 자동으로 유도됩니다. `MULTICA_PUBLIC_URL`이 설정되어 있으면 그것을, 없으면 `MULTICA_APP_URL`(또는 `FRONTEND_ORIGIN`)을 사용합니다. 둘 다 공급자가 리디렉션할 origin을 나타내지 못할 때만 `OIDC_REDIRECT_URI`를 직접 지정하세요.

### 3. API 재시작

로그인 페이지에 **Keycloak(으)로 계속** 버튼이 표시됩니다. 설정은 런타임에 `/api/config`에서 읽으므로 프런트엔드 이미지를 다시 빌드할 필요가 없습니다. 데스크톱 앱에도 같은 버튼이 나타나며, 브라우저를 열어 로그인을 마칩니다.

### 계정을 연결하는 방식

Multica는 `email` claim으로 사용자를 식별합니다. 이미 Multica 계정이 있는 주소는 그 계정으로 로그인하고, 그 외에는 아래 [가입 범위 제어](#가입-범위-제어)의 제약을 받으며 새 계정이 만들어집니다. 도입 전에 알아 둘 점이 두 가지 있습니다.

- **ID 공급자가 이메일을 보내야 합니다.** `email` scope를 부여하고, 해당 claim이 ID token 또는 userinfo 응답에 매핑되어 있는지 확인하세요.
- **ID 공급자가 주소를 미확인(`email_verified: false`)으로 보고하면 로그인이 거부됩니다.** 그렇지 않으면 IdP에 스스로 등록할 수 있는 사람이 이메일 일치만으로 동료의 계정을 차지할 수 있기 때문입니다. claim 자체를 보내지 않는 공급자는 허용됩니다.

ID 공급자가 외부 ID를 페더레이션한다면 `ALLOWED_EMAIL_DOMAINS`에 회사 도메인을 지정하세요.

### Scope

기본으로 `openid email profile`을 요청합니다. `OIDC_SCOPES`(쉼표 또는 공백 구분)로 추가할 수 있으며, `openid`는 생략해도 자동으로 추가됩니다.

### 문제 해결

| 증상 | 의미 |
|---|---|
| SSO 버튼이 없음 | `OIDC_ISSUER` / `OIDC_CLIENT_ID` / `OIDC_CLIENT_SECRET` 중 하나가 비어 있습니다. 어느 것인지는 API 시작 로그에 남습니다 |
| "SSO가 구성되어 있지 않습니다" | `MULTICA_APP_URL`, `MULTICA_PUBLIC_URL`, `OIDC_REDIRECT_URI`가 모두 비어 있어 callback URL을 유도할 수 없습니다 |
| "ID 공급자가 이 요청을 거부했습니다" | client id, client secret, callback URL 중 하나가 공급자에 등록된 값과 다릅니다 |
| "이번 로그인 시도가 만료되었거나 이미 사용되었습니다" | 로그인이 15분을 넘겼거나 브라우저가 트랜잭션 cookie를 버렸습니다. `COOKIE_DOMAIN`이 API 호스트를 포함하는지 확인하세요 |
| "이메일 주소를 제공하지 않았습니다" | 클라이언트에 `email` scope 또는 이메일 claim mapper가 없습니다 |

## 가입 범위 제어

세 변수가 새 계정을 만들 수 있는지 함께 결정합니다.

| 변수 | 역할 |
|---|---|
| `ALLOWED_EMAILS` | 허용할 전체 이메일 주소, 여러 값은 쉼표로 구분 |
| `ALLOWED_EMAIL_DOMAINS` | 허용할 이메일 도메인, 여러 값은 쉼표로 구분 |
| `ALLOW_SIGNUP` | allowlist가 없을 때 가입 허용 여부, 기본값 `true` |

판단 순서는 다음과 같습니다.

1. 이메일이 `ALLOWED_EMAILS`와 일치하면 허용합니다.
2. 또는 도메인이 `ALLOWED_EMAIL_DOMAINS`와 일치하면 허용합니다.
3. 어느 것과도 일치하지 않고 `ALLOW_SIGNUP=false`이면 거부합니다.
4. `ALLOW_SIGNUP=true`여도 하나 이상의 allowlist가 설정되어 있고 일치하지 않으면 거부합니다.
5. allowlist가 없고 `ALLOW_SIGNUP=true`이면 허용합니다.

일반적인 설정:

```dotenv
# 회사 도메인만 허용
ALLOW_SIGNUP=false
ALLOWED_EMAIL_DOMAINS=company.com

# 외부 협업자 한 명 추가 허용
ALLOWED_EMAILS=partner@example.net
```

<Callout type="info">
`ALLOW_SIGNUP=false`일 때도 두 allowlist를 명시적인 예외 목록으로 사용할 수 있습니다.
</Callout>

## 초대와 가입 제한

초대는 가입 제한을 자동으로 우회하지 않습니다.

- 상대방에게 이미 Multica 계정이 있으면 로그인하고 초대를 수락할 수 있습니다.
- 상대방에게 계정이 없으면 이메일이 위의 가입 규칙을 만족해야 합니다.

공개 가입을 닫은 인스턴스에서 새 멤버를 초대할 때는 먼저 상대방 이메일을 `ALLOWED_EMAILS`에 추가하세요. 계정을 만들고 초대를 수락한 뒤 목록에서 다시 제거할 수 있습니다.

## 로그인 유효 기간

세션은 슬라이딩 갱신됩니다. 아래 값은 로그인 시점부터의 카운트다운이 아니라 **유휴** 한도입니다. 남은 유효 기간이 절반 아래로 내려가면 다음 요청에서 전체 기간으로 다시 발급되므로, 계속 사용하는 계정이 주기적으로 로그아웃되지 않습니다. 절대 상한은 없습니다.

이 한도는 한쪽 방향으로만 적용됩니다. 절반 아래로 내려간 뒤에야 다시 발급되므로, 마지막 사용 시점에 절반 이상 남아 있던 세션은 연장되지 않습니다. 항상 견딜 수 있는 유휴 시간은 아래 값의 절반입니다.

`AUTH_TOKEN_TTL`로 조정할 수 있으며 Go duration 또는 양의 정수 초를 지원합니다.

```dotenv
AUTH_TOKEN_TTL=720h
```

최솟값은 `60s`이며, 더 짧은 값은 `60s`로 조정되고 시작 시 경고가 기록됩니다. 이보다 짧으면 서버가 계산한 갱신 확인 주기가 클라이언트의 하한보다 낮아져, 세션이 유지될 수 있는 시간보다 드물게 확인하게 됩니다.

변경 후 API 서비스를 다시 시작해야 합니다. 이 값은 이후 발급되거나 다시 발급되는 세션에 적용됩니다. 세션은 슬라이딩 갱신되므로 기존 세션도 다음 재발급 때 새 기간을 적용받습니다.
