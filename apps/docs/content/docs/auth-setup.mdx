Multica signs users in with email verification codes by default; Google OAuth can be added on top. Existing users can always sign in again — signup restrictions only decide whether new accounts can be created.

## Email verification codes

After the user enters an email address, Multica sends a 6-digit verification code. The code is valid for 10 minutes; once it verifies, the browser receives a sign-in cookie.

Email can be delivered through Resend or SMTP. When both are configured, `SMTP_HOST` takes priority.

### Using Resend

1. Verify a sending domain and create an API key at [Resend](https://resend.com/).
2. Set:

   ```dotenv
   RESEND_API_KEY=re_xxxxxxxxxxxxxxxx
   RESEND_FROM_EMAIL=noreply@example.com
   ```

3. Restart the API service.

`RESEND_FROM_EMAIL` must belong to a domain already verified in Resend.

### Using SMTP

At minimum, set the host and sender address:

```dotenv
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USERNAME=multica
SMTP_PASSWORD=<password>
SMTP_FROM_EMAIL=noreply@example.com
```

Common connection modes:

| Scenario | Configuration |
|---|---|
| Internal anonymous relay | `SMTP_PORT=25`, leave username and password empty |
| STARTTLS | `SMTP_PORT=587`; upgrades to TLS by default when the server supports it |
| Implicit TLS | `SMTP_PORT=465`, or set `SMTP_TLS=implicit` explicitly |

If `SMTP_FROM_EMAIL` is unset, it falls back to `RESEND_FROM_EMAIL`. Private CAs or self-signed certificates require adding the CA to the container trust store; `SMTP_TLS_INSECURE=true` skips certificate verification and should only be used temporarily on a trusted internal network.

Some strict relays also require a valid EHLO name:

```dotenv
SMTP_EHLO_NAME=mail.example.com
```

### Behavior without an email service

The server still starts, but verification codes and invitation links are only written to the log; no email is sent. This suits local development, not production.

The startup log states whether the current mode is `Resend API`, `SMTP relay`, or `DEV mode`.

## Fixed local verification code

Local automated tests can set a fixed verification code:

```dotenv
APP_ENV=development
MULTICA_DEV_VERIFICATION_CODE=888888
```

The code must be 6 digits. The fixed code is ignored when `APP_ENV=production`.

<Callout type="warning">
Do not enable a fixed code on a publicly reachable instance. The production combination is `APP_ENV=production` with an empty `MULTICA_DEV_VERIFICATION_CODE`.
</Callout>

## Google sign-in

1. Create an OAuth 2.0 client in the [Google Cloud Console](https://console.cloud.google.com/).
2. Add the Multica frontend's callback URL to **Authorized redirect URIs**:

   ```text
   https://multica.example.com/auth/callback
   ```

3. Set:

   ```dotenv
   GOOGLE_CLIENT_ID=xxxxx.apps.googleusercontent.com
   GOOGLE_CLIENT_SECRET=GOCSPX-xxxxxxxxxxxxxxx
   GOOGLE_REDIRECT_URI=https://multica.example.com/auth/callback
   ```

4. Restart the API service.

The URLs in the Google Console and in `GOOGLE_REDIRECT_URI` must match exactly, including protocol, port, and trailing slash. Once configured, the sign-in page shows a Google sign-in button; the frontend image needs no rebuild.

## Single sign-on (OIDC)

Multica speaks standard OpenID Connect, so any provider that publishes a discovery document works: Keycloak, Authentik, Okta, Auth0, Entra ID. The walkthrough below uses Keycloak; the variables are the same everywhere.

### 1. Register a client with your provider

In Keycloak, open your realm and create a client:

- **Client type**: `OpenID Connect`
- **Client authentication**: `On` — Multica is a confidential client and always sends a secret
- **Valid redirect URIs**: the callback below, exactly

```text
https://multica.example.com/auth/oidc/callback
```

<Callout type="warning">
Providers match this byte-for-byte, so the protocol, port and trailing slash all have to agree. Use your Multica origin — the same host you sign in at. If your API runs on a separate host, use the **API** origin instead, because that is where `/auth/oidc/callback` is served.
</Callout>

Copy the generated client secret from the client's **Credentials** tab.

### 2. Configure Multica

```dotenv
OIDC_ISSUER=https://sso.example.com/realms/multica
OIDC_CLIENT_ID=multica
OIDC_CLIENT_SECRET=xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
OIDC_PROVIDER_NAME=Keycloak
```

`OIDC_ISSUER` is the base URL whose `/.well-known/openid-configuration` describes the provider — for Keycloak, `<base>/realms/<realm>`. Confirm it before restarting:

```bash
curl -s https://sso.example.com/realms/multica/.well-known/openid-configuration | head
```

The callback URL is derived for you: `MULTICA_PUBLIC_URL` when set, otherwise `MULTICA_APP_URL` (or `FRONTEND_ORIGIN`). Set `OIDC_REDIRECT_URI` explicitly only if neither describes the origin the provider should redirect to.

### 3. Recreate the API container

```bash
docker compose -f docker-compose.selfhost.yml up -d backend
```

Use `up -d`, not `restart`: Compose fixes a container's environment when it is **created**, so `restart` replays the old values and your new `OIDC_*` settings never reach the server.

The sign-in page then shows a **Continue with Keycloak** button. It reads everything from `/api/config` at runtime, so the frontend image needs no rebuild. The desktop app shows the same button and opens your browser to complete the flow.

### How accounts are matched

Multica identifies people by the `email` claim: an address that already has a Multica account signs in to that account, and anything else creates a new one subject to the [signup restrictions](#signup-restrictions) below. Two consequences worth knowing before you roll this out:

- **The provider must send an email.** Grant the `email` scope and make sure the claim is mapped into the ID token or the userinfo response.
- **A sign-in is refused when the provider reports the address as unverified** (`email_verified: false`), because account matching by email would otherwise let anyone who can self-register at your IdP claim a colleague's account. A provider that omits the claim entirely is accepted.

Set `ALLOWED_EMAIL_DOMAINS` to your corporate domain if your provider federates external identities.

### Scopes

`openid email profile` is requested by default. Add more with `OIDC_SCOPES` (comma- or space-separated); `openid` is added back automatically if you leave it out.

### Troubleshooting

| What you see | What it means |
|---|---|
| No SSO button | One of `OIDC_ISSUER` / `OIDC_CLIENT_ID` / `OIDC_CLIENT_SECRET` is unset. The API logs which at startup |
| "Single sign-on is not configured" | `MULTICA_APP_URL`, `MULTICA_PUBLIC_URL` and `OIDC_REDIRECT_URI` are all empty, so no callback URL can be derived |
| "Your identity provider rejected the request" | The client id, secret or redirect URI does not match what the provider has registered |
| "This sign-in attempt expired or was already used" | The login took longer than 15 minutes, or the browser dropped the transaction cookie. Check that `COOKIE_DOMAIN` covers the API host |
| "did not share an email address" | The client is missing the `email` scope or an email claim mapper |

## Signup restrictions

Three variables together decide whether a new account can be created:

| Variable | Effect |
|---|---|
| `ALLOWED_EMAILS` | Full email addresses allowed to sign up, comma-separated |
| `ALLOWED_EMAIL_DOMAINS` | Email domains allowed to sign up, comma-separated |
| `ALLOW_SIGNUP` | Whether signup is allowed when no allowlist is configured; defaults to `true` |

The evaluation order is:

1. The email matches `ALLOWED_EMAILS` — allow.
2. Or its domain matches `ALLOWED_EMAIL_DOMAINS` — allow.
3. With no match, if `ALLOW_SIGNUP=false` — reject.
4. With `ALLOW_SIGNUP=true` but any allowlist configured and no match — still reject.
5. With no allowlist configured and `ALLOW_SIGNUP=true` — allow.

Common configurations:

```dotenv
# Company domain only
ALLOW_SIGNUP=false
ALLOWED_EMAIL_DOMAINS=company.com

# Also admit one external collaborator
ALLOWED_EMAILS=partner@example.net
```

<Callout type="info">
Both allowlists also work as an explicit exception list when `ALLOW_SIGNUP=false`.
</Callout>

## Invitations and signup restrictions

Invitations do not automatically bypass signup restrictions:

- If the invitee already has a Multica account, they can sign in and accept the invitation.
- If they do not, their email must satisfy the signup rules above.

To invite a new member on an instance with open signup disabled, add their email to `ALLOWED_EMAILS` first. Once the account is created and the invitation accepted, you can remove the entry again.

## Session lifetime

Sessions slide. The lifetime below is an **idle** bound, not a countdown from sign-in: once a session drops below half of it, the next request re-issues it with a full lifetime again, so an account in continuous use is never signed out on a schedule. There is no absolute cap.

The bound is one-sided. A session is only re-issued once it is past the halfway point, so a session last used while it still had more than half its lifetime left is not extended — the idle gap that is always survivable is half the value below, not all of it.

Adjust with `AUTH_TOKEN_TTL`, which accepts a Go duration or a positive integer of seconds:

```dotenv
AUTH_TOKEN_TTL=720h
```

The minimum is `60s`; anything shorter is clamped up to it and logs a warning at startup. Below that, the renewal cadence the server derives would fall under the floor clients apply to it, and clients would check for renewal less often than the session can survive.

Restart the API service after changing it. The value applies to sessions issued or re-issued afterwards — because sessions slide, an existing session picks up the new lifetime the next time it is re-issued.
